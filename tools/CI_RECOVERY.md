# 云效探针仓库 —— 灾难恢复手册

> 触发条件：阿里云文档写明「欠费后立即停机，停机满 15 天释放所有云效组织，
> **研发数据无法找回**」。本手册 + `tools/restore_codeup.py` 覆盖全部恢复流程。

## 关键认知：什么能自动恢复，什么不能

| | 能否自动恢复 | 靠什么 |
|---|---|---|
| 仓库内容（代码 / 22MB mihomo 内核 / vendor yaml / 节点配置） | ✅ 能 | `tools/restore_codeup.py --apply` |
| **流水线配置（那条命令 + cron 触发器）** | ❌ **不能** | 本手册手工重建 |
| 采集到的历史探针数据 | ⚠️ 看情况 | 若已推到 Gitee 备份则可找回 |

**流水线配置存在云效自己的数据库里，不在 git 里。** 任何脚本都救不了它。
所以每次改流水线配置，**必须同步更新 `tools/ci_probe_command.sh` 与本文件**。

## 场景一：云效组织被删除（欠费 15 天到期）

### 1. 重建组织

阿里云控制台 → 云效 → 创建组织

- **协作模式：个人使用模式**（最多 5 人，**0 元**）
  - ⚠ 千万不要选「企业协作模式」：按**日峰值人数 2 元/人/天**计费，
    组织创建当天就产生费用。
- ⚠ 不要开通按量计费，除非你打算一直用；开通后余额归零会立刻停机。

### 2. 建仓库

代码管理 → 新建代码仓库，路径**必须是**：

```
codeup/ci-probe-test
```

- **不要初始化 README**（留空仓，脚本会 clone 后在其上提交）

### 3. 恢复内容

```powershell
cd D:\work\agent\codebuddy\clash-source
python tools\restore_codeup.py          # 先预演，看现状
python tools\restore_codeup.py --apply  # 执行
```

脚本会：
1. clone 空仓
2. 从本机主仓（唯一来源）组装全部内容
3. commit + push
4. **逐文件 sha256 校验**，确认 32 个文件（含 22MB 内核）与预期一致

如果本机主仓也没了，可以从 Gitee 备份恢复：

```powershell
python tools\restore_codeup.py --apply --from-gitee
```

### 4. 重建流水线

流水线 → 新建流水线

| 字段 | 值 |
|---|---|
| 模板 | **空模板 / 其他 / 执行命令**（不要选 Node/Java/Go，那些会塞一堆构建步骤） |
| 代码源 | `codeup/ci-probe-test` |
| 默认分支 | `master` |
| 构建集群 | **云效杭州构建集群**（集群系数 1；香港是 2、VPC 需自备资源） |
| 指定构建节点 | Linux/amd64 |

执行命令粘这一行（见 `tools/ci_probe_command.sh`）：

```bash
bash tools/sync_and_probe.sh
```

### 5. 定时触发

触发设置 → 定时触发 → cron（**6 位，第一位是秒**）：

```
0 23 4 * * *
```

= **每天** 04:23。若不接受 `*` 作为星期，写 `0 23 4 * * ?`。

> ⚠ 这里原来是 `0 23 4 * * SUN`（**每周日**），2026-10-16 核对 Codeup 提交历史后
> 改成每天：10-16（**周五**）当天 04:24 与 04:31 各有一轮探针提交，说明实际
> 定时器本来就是日频，只是本手册写的与线上不一致 —— 按手册重建会把频率降到 1/7。
> 重建后**一定要用提交历史核对**（`git log --date=iso`，看是否有当天的
> `cnci 探针 YYYYMMDD-HHMM`），别信手册。

> 为什么是 04:23 而不是整点：整点是流量高峰，容器调度最容易排队。
> 与本机任务（12:30）错开 8 小时。

### 6. 验证

手动跑一次，看是否出现：

```
[cnci] mihomo: Mihomo Meta v1.19.32 linux amd64 ...
[cnci] PyYAML 5.4.1（vendor，纯 Python: True）...
[cnci] scope=cnci 抽样=30/源  hc_timeout=8000ms 用时=XXs
[cnci] 源: 12 个（已收敛 12，未测完 0）
[cnci] 结果已推回 Codeup: results/probe_cnci-<时间戳>.json
```

然后去 Codeup 仓库确认出现了 `results/` 目录 —— **那才说明采集数据开始积累了**。

再确认一件同样重要的事：**回传主仓有没有真的成功**。

```powershell
python tools\cnci_status.py
```

这一段的成败**不会让流水线变红**（刻意设计：日志面板不可靠，红了只会掩盖真失败），
所以它每轮会往 Codeup 仓落一份 `results/push_main_last.json` 留痕 ——
上面那条命令就是读它，直接告诉你「回传正常 / 不通 + 原因 / 还没留痕过」。
前提是流水线变量里有 `GH_PAT`（缺失时脚本**直接跳过且不报错**，
留痕会把这种情况标成 `status=no-pat`）。

⚠ 2026-10-16 之前，主仓里那些 `results/` 与 `state/probe_cnci_latest.json`
全是**本机手工补的**（主仓历史里有「删除误推的合成存档」这种提交）。
别把它们当成「回传通了」的证据 —— 留痕是 2026-10-16 才加的，
**如果 `cnci_status.py` 说「还没留痕」，就说明带留痕的那版还没在云效上跑过**。

## 场景二：只是仓库被删 / 内容被清空

跳过步骤 1、2，直接从步骤 3 开始。

## 场景三：令牌过期（推送报「Https克隆账号或密码错误」）

云效 Codeup → 个人设置 → **重新生成个人访问令牌**（勾代码仓库读写）

然后改写 `codeup.https` 的第二行。注意：

- **用户名是云效「登录账号」，不是组织前缀 `myxk`**
  （页面提示「请使用登录账号 / 个人令牌进行克隆」）
- **登录密码含 `@` 不能用在 URL 里**（git 会报 `URL rejected: Bad hostname`），
  所以必须用令牌
- `tools/codeup_auth.py` 会自动试出可用组合并写回该文件

## 防患于未然（强烈建议做）

去 **阿里云控制台 → 费用中心 → 费用告警**，加一条规则：
**月度费用超过 1 元就发短信。**

理由：云效免费额度 3000 核分/月，**每天一轮**（每轮 ~11 核分）= 约 77 核分/月（**2.6%**）。
正常情况永远不会产生费用——但一旦额度策略调整、或组织里多了别的东西，
账单会悄悄累积，而它的后果是**静默停机 15 天后删除整个组织**，
你根本不会注意到。一条 1 元的告警是防止数据被静默删除最便宜的手段。

## 附：四层架构与各自的恢复方式

| 层 | 位置 | 频率 | 权限 | 出事怎么恢复 |
|---|---|---|---|---|
| L1 | 美国 GitHub Actions | 每 6 小时全量 | **判死** | 源码在 public 仓，重建 workflow 即可 |
| L2 | 本机 Windows 计划任务 | 每日 12:30 全量 | **回收** | `src/local_probe.py` 在主仓，重建计划任务 |
| L3 | 云效杭州 | **每天 04:23** 抽样 | 交叉验证 | **本手册** |
| 备份 | Gitee `andywx/ci-probe-test` | — | — | 内容与 Codeup 逐字节一致 |

L1/L2 的失效都是"保守失败"（差源不下线 / 好源不回收），不会让系统变坏。
只有 L3 会造成"无人在国内盯着"这种软损失。
